## 1. 项目摘要

留灯是一款面向离家人群的低打扰智能看护助手。它接入 eufy 摄像头，通过云端结合短期计划与长期记忆，将画面变化整理为事件、提醒和日报，并让网页、iPhone 与 Apple Watch 共享同一份信息。

我们希望解决的核心问题是：用户离开家后，能够完成一次有依据的确认，再回到自己的生活。产品因此把重点放在“发生了什么、是否符合预期、需不需要处理”，而不只是提供更多监控画面和运动通知。

我在项目中主要承担产品经理、全栈开发和 Pitch 工作，将用户场景、交互方案、跨端实现和现场表达串联起来。团队完成了网页、iPhone 与 Apple Watch 的原型及工程交付；比赛时期的联调记录确认了三端真实画面和时间更新。完整事件判断、提醒及跨端确认闭环仍有待验收。

**参赛结果：**据本人确认，团队于 2026 年 10 月入围本届 Anker 黑客松。现场照片显示赛事共有 1,817 名报名者、308 支提交预赛的队伍、33 支最终入围队伍；其中智能安防赛道为 8 支。照片反映赛事总体规模，不单独证明本团队的入围身份。当前可使用“入围”表述，不写未经确认的获奖名次。

## 2. 用户问题与产品机会

### 2.1 目标用户

核心用户是工作、出行期间仍牵挂家中情况的人：他们希望知道家里是否正常，却不方便持续打开监控、翻看片段或逐条判断通知。

比赛阶段选择“外卖送达与取走”作为主要演示场景，便于用可观察的物品变化展示从画面到事件、再到用户确认的流程。门锁、水电与全屋看护属于后续扩展方向，需要相应设备与能力接入。

### 2.2 问题拆解

| 用户遇到的问题 | 对应产品需求 |
| --- | --- |
| 看到了画面，却仍需自己判断发生了什么 | 将关键画面组织成有时间线的事件摘要 |
| 收到变化通知，却不知道是否值得关注 | 引入短期计划与长期习惯作为判断上下文 |
| 同一件事在不同设备上需要重新寻找 | 通过共享云端向多端提供统一信息 |
| 看完后仍不知道该做什么 | 提供查看依据、确认与反馈入口 |
| 断线或旧画面容易被误认为当前状态 | 显示更新时间、连接状态及画面过期提示 |

这些是项目的需求判断与设计假设。已有会议及需求记录支持方向形成过程，但目前没有可核验的大规模访谈、用户样本或使用效果数据。

### 2.3 产品定位

**一句话定位：**结合用户安排与习惯，把家庭摄像头的变化整理成可理解、可确认的事件，让安心跟得上生活。

核心价值假设包括：减少重复查看、降低无关信息打扰、保留事件依据，并让用户跨设备接续处理同一件事。上述价值需要后续用户测试验证。

## 3. 产品目标与 MVP 范围

### 3.1 产品目标

1. 让用户先确认画面是否新鲜，再了解发生了什么。
2. 将“短期计划”和“长期记忆”引入事件解释。
3. 用不同设备承接不同深度的查看与操作。
4. 在比赛阶段交付可展示的真实设备链路，并明确原型与实际能力的区别。

### 3.2 核心功能

| 模块 | 产品作用 | 当前实现与边界 |
| --- | --- | --- |
| 当前画面 | 快速查看家中情况 | 既有记录确认三端真实画面联通；手机、手表约每五秒更新 JPEG，非连续音视频直播 |
| 事件与提醒 | 理解变化、筛选需要关注的事项 | 云端包含判断、事件合并与提醒逻辑；完整业务闭环未全部验收 |
| 短期计划 | 表达某个时间段的预期 | 已有新增、编辑、时间范围与启用状态相关实现 |
| 长期记忆 | 记录可纠正的用户习惯 | 已有查看、编辑与启用状态相关实现 |
| 对话与草稿确认 | 通过交流调整计划或记忆 | 已有模型调用及草稿确认相关实现；不直接将模型建议无确认地写入 |
| 今日与日报 | 按天回顾事件 | 已有页面及云端逻辑；质量和长期使用效果待验证 |
| 多端共享 | 在不同屏幕接续查看 | 共享云端架构已建立；画面同步记录不替代全部操作一致性验收 |

## 4. 核心用户流程

以外卖场景为例，目标体验如下：

1. **设置预期：**用户创建某个时间段的外卖送达计划。
2. **观察变化：**摄像头捕捉门前物品或人员变化，采集页上传画面及片段。
3. **整理事件：**云端结合计划、记忆和关键画面进行分析，形成事件与提醒。
4. **快速查看：**用户在手表上看缩略图、时间与提醒，判断是否需要进一步操作。
5. **展开依据：**用户在手机上查看送达、取走等经过及相关画面。
6. **确认处理：**用户确认领取或回看异常依据，目标是让事件获得明确结果。

这是产品目标流程。真实画面查看已见于联调记录；从外卖识别到领取确认归档的完整链路，不据此宣称全部完成。

### 三端职责

| 终端 | 用户任务 | 设计重点 |
| --- | --- | --- |
| 网页 | 看全局、查看事件；采集端另承接设备接入 | 复用采集能力，支撑演示及联调 |
| iPhone | 展开详情、编辑计划与记忆、对话和确认 | 适合较完整的信息与操作 |
| Apple Watch | 短时查看、快速确认当前状态 | 缩略画面、时间、最近事件与提醒 |

## 5. 关键产品决策与迭代

### 5.1 从管理台转向简洁查看体验

早期方案功能层级偏多。根据团队讨论，Web 原型将首页收敛为画面、提示、短期计划与长期记忆入口，以及底部输入；编辑和管理按需展开。目的在于让用户首先获得当下需要的信息，减少在管理界面中寻找的成本。

后续原生 iPhone 端使用“此刻、计划、记忆、对话”四页组织任务。Web 原型与原生 App 是不同阶段、不同终端的设计，不能将早期单页要求描述为所有端最终一致的结构。

### 5.2 把上下文作为事件判断的一部分

同样一次画面变化，在不同时间与用户安排下可能有不同含义。产品引入短期计划与长期记忆，让云端有机会区分符合预期的活动与需要关注的变化，并保留用户纠正入口。

### 5.3 让 AI 建议可检查、可确认

对话转成计划或记忆时先进入草稿，由用户确认后保存。该交互让用户能够校正模型对时间、内容和习惯的理解，避免把一次模型输出直接当成用户意图。

### 5.4 将信息新鲜度纳入体验

连接状态、画面时间、过期标识与重连逻辑直接影响用户能否相信当前画面。手机端已有前台重试、推送心跳超时重连、画面过期取消实时标识和后台暂停等实现；这些是演示可靠性与产品可信度的重要部分。

## 6. 技术方案与工程交付

```text
eufy 摄像头
    ↓
Chrome 采集页／SDK 适配：获取画面与片段
    ↓
Node 云端 Homi：分析、事件、提醒、计划、记忆、日报与存储
    ↓ HTTPS / SSE
React 网页 ｜ SwiftUI iPhone ｜ SwiftUI Apple Watch
    ↑ HTTP 操作回传云端
```

| 层次 | 技术与职责 |
| --- | --- |
| Web | React、TypeScript、Vite；用户页面、摄像头采集与调试入口 |
| 云端 | Node.js、TypeScript；鉴权、共享状态、事件处理、模型代理与持久化 |
| 通信 | HTTP 请求处理操作，SSE 推送画面、共享状态与心跳 |
| 原生端 | SwiftUI iOS / watchOS；各端界面、云端连接与状态展示 |
| 设备依赖 | 主办方 eufy 授权 SDK、持续运行的采集页及网络连接 |

当前手表直接访问云端，不依赖 iPhone 经 WatchConnectivity 转发。这让两端共享同一服务，但仍需处理各自的网络与系统后台限制。

仓库包含事件合并、记忆应用、画面处理、日报、数据保留与同步差异等测试文件；本次文档整理未重新构建或运行测试，不将测试文件存在等同于当前全部通过。

## 8. 项目成果与验证边界

### 已有成果

- 2026 年 10 月入围 Anker 首届黑客松挑战赛，参与智能安防赛道。
- 形成网页、iPhone 与 Apple Watch 的产品方案、交互原型与代码交付。
- 比赛时期联调记录确认手机、手表等端真实画面及时间更新；已形成共享云端链路。
- 交付需求说明、API 与开发交接、版本状态、比赛材料和多版 Pitch 稿。
- 将代码与交互资料整理至公开 GitHub 仓库，便于展示与后续接续。

### 尚不能写成已验证成果

- 未提供识别准确率、误报率、通知减少比例、用户留存或商业收入数据。
- 完整事件判断、提醒、跨端确认与归档闭环尚未全部验收。
- 系统级 APNs 后台推送、原生双向对讲、独立语音识别及连续音视频体验未完整实现。
- Android 端有 OPPO 适配原型，归档中没有可安装 Android 工程。
- 手表最新重连及中文名称修改已编译，但历史记录显示最新安装未成功；Siri 唤起未验证。
- 当前架构仍依赖持续运行的采集电脑及浏览器，尚未完成长期无人值守稳定性验证。
